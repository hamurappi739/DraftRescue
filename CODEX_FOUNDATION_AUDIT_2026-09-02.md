# DraftRescue — аудит foundation-пакета для автора спецификаций

**Дата аудита:** 2026-09-02  
**Статус:** код не изменялся; выводы основаны на фактической структуре, скриптах и контрольных артефактах пакета.

## Краткий вывод

Пакет хорошо подготовлен как specification-first foundation. Границы приватности, порядок фаз, ADR и критерии приёмки согласованы. Основная проблема не в архитектуре, а в том, что Phase 0 пока нельзя честно считать верифицированной: на текущей Windows-машине нет .NET SDK, а PowerShell-проверка сообщает об успехе даже после неуспешных `dotnet restore`, `build` и `test`.

## Подтверждённые проблемы

### F-001 — `verify.ps1` даёт ложный успешный результат

**Серьёзность:** высокая.  
**Файл:** `scripts/verify.ps1`.

Скрипт вызывает внешние команды `dotnet restore`, `dotnet build` и `dotnet test`, но не проверяет `$LASTEXITCODE` после каждой из них. `$ErrorActionPreference = 'Stop'` не превращает ненулевой код завершения внешней программы в PowerShell-исключение.

На текущей машине `dotnet --info` подтвердил отсутствие SDK. Все три команды завершились ошибкой, однако скрипт напечатал `Phase 0 verification passed.` Это создаёт риск начать Phase 1, не имея работающей базы.

**Нужная правка:** после каждого внешнего вызова немедленно прерывать скрипт при ненулевом `$LASTEXITCODE` (или использовать обёртку `Invoke-Checked`); вернуть/вывести ненулевой код процесса. `scripts/verify.cmd` уже делает это корректно через `|| exit /b 1` и может служить образцом.

**Приёмка:** временно запустить проверку без SDK либо с намеренно неверной solution-path — PowerShell-скрипт обязан завершиться с ошибкой и не печатать сообщение об успехе.

### F-002 — обязательный Phase-0 gate фактически не пройден

**Серьёзность:** высокая, блокирующая дальнейшую реализацию.  
**Затрагивает:** `CODEX_START_HERE.md`, `README.md`, `docs/PHASE_0_REVIEW_CHECKLIST.md`.

В окружении имеется .NET 8 runtime, но отсутствует любой .NET SDK. Поэтому NuGet restore, build, test и ручной запуск Avalonia-shell не подтверждены на реальной машине. Это прямо соответствует исходному handoff-статусу, но требует устранения до первого WP Phase 1.

**Нужное действие:** установить .NET 8 SDK для Windows x64, затем выполнить `scripts\\verify.cmd` и исправленный `scripts/verify.ps1`; отдельно открыть Avalonia shell. Если появятся ошибки, исправлять только Phase 0.

### F-003 — manifest/count metadata устарели относительно фактического состава

**Серьёзность:** низкая, но ухудшает доверие к handoff.

`FOUNDATION_MANIFEST.md` называет 361 файл и 265 Markdown-файлов. До добавления этого аудита фактическая инвентаризация находила 363 файла и 270 Markdown-файлов. При этом 360 записей `FOUNDATION_SHA256SUMS.txt` проверены: несовпадений хешей нет.

**Нужная правка:** после согласования состава пакета единообразно пересобрать `FOUNDATION_FILE_INVENTORY.txt`, `FOUNDATION_SHA256SUMS.txt` и числовые поля в `FOUNDATION_MANIFEST.md`. Включить в описание правило: какие служебные файлы намеренно исключаются из checksum-list.

### F-004 — воспроизводимость SDK не закреплена

**Серьёзность:** средняя.

В корне есть `global.json`, но он задаёт только test runner и не закрепляет версию SDK. `Directory.Build.props` требует `net8.0`, однако разные SDK 8.x могут по-разному влиять на restore, анализаторы и Avalonia/XAML build.

**Нужная правка:** после первого успешного Windows build зафиксировать согласованную версию SDK в `global.json` (с подходящим `rollForward`) либо явно документировать поддерживаемый диапазон SDK и проверить его в CI/verify script.

## Не дефекты, а важные факты handoff

- В репозитории реализован только Phase-0 skeleton: 5 слоёв, минимальный Avalonia shell, базовые privacy-safe contracts и 4 исходных test-файла.
- 229 тестов в registry — это целевой каталог/матрица, а не 229 уже реализованных автотестов. Это стоит особенно явно сохранять в статусных документах, чтобы следующий агент не интерпретировал дизайн как готовую функциональность.
- Открытые решения корректно вынесены в `docs/OPEN_DECISIONS.md`. Их нельзя закрывать внутри несвязанного WP; особенно это относится к Windows/UIA event topology, browser private-mode detection, стратегии чтения разных control families и direct Restore.
- Физическая перестановка 270 Markdown-документов сейчас не рекомендуется: действующая плоская структура компенсирована `docs/INDEX.md`, фазовыми package-index файлами, а перенос потребует массового обновления ссылок и контрольных хешей. Сначала лучше завершить Phase 0.

## Рекомендуемый порядок следующей работы

1. Установить .NET 8 SDK x64.
2. Исправить только F-001 в рамках WP-0.1.
3. Запустить оба verification-скрипта, `dotnet restore/build/test` и вручную Avalonia shell.
4. Обновить handoff/manifest после стабильного Phase-0 результата.
5. Только затем начинать один строго ограниченный пакет Phase 1: WP-1.1 (foreground application prototype), без UIA text reads и без keyboard hooks.

## Что в пакете сделано особенно хорошо

- Privacy boundary определена раньше, чем механизмы захвата текста.
- Принцип `classification before content read` закреплён одновременно в ADR, фазах, типах и тестовых планах.
- Phase 2 capability и Phase 3/4 boundaries не дают незаметно превратить продукт в keylogger.
- SQLite/DPAPI design исключает plaintext repository API, WAL по умолчанию и revision history.
- Recovery/Restore задуман консервативно: metadata-only list, explicit reveal, fresh security check, deterministic evidence lattice и отсутствие force-restore.
