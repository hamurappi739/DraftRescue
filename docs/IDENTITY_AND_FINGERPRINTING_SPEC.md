# Identity and Fingerprinting Specification

**Status:** accepted design baseline for future implementation.

## 1. Problem

DraftRescue needs enough stable context to correlate a recoverable draft with a later field while minimizing stored user-visible metadata. Raw window titles, full URLs, labels, accessible names, and nearby text may contain private information and should not become durable metadata just because draft text itself is encrypted.

## 2. Principle

Persist versioned **keyed fingerprints**, not raw strings, whenever matching does not require the raw value.

A plain SHA-256 hash is not the default because low-entropy values such as common page titles/domains can be dictionary-tested. Use HMAC-SHA-256 with a random installation-local key.

## 3. Fingerprint key

`FingerprintKeyV1`:

- 32 random bytes generated by a CSPRNG at first successful initialization;
- protected at rest with Windows DPAPI using `CurrentUser` scope;
- never logged;
- never synced;
- not exposed to UI;
- stored separately from draft database records;
- failure to load/unprotect means matching features fail closed; do not silently generate a new key while old drafts still exist.

A deliberate key reset invalidates existing correlation metadata and therefore requires discarding existing recoverable drafts.

## 4. Normalization before HMAC

Each signal has a dedicated canonical normalization function and namespace.

Conceptual input:

```text
HMAC(key, "drfp:v1:<signal-kind>:" + UTF8(normalizedValue))
```

Never concatenate multiple untyped values without separators/namespaces.

## 5. Stored token size

Store the first 16 bytes (128 bits) of HMAC-SHA-256 for ordinary equality matching. Keep the algorithm/version in metadata. This is not a password hash; the secret HMAC key provides resistance to offline guessing of low-entropy metadata.

## 6. Signal policy

### Application executable identity

May persist a normalized non-secret application ID directly when it is a known product identifier. Raw arbitrary executable paths should not be required for ordinary recovery UI.

### Window title

- do not persist raw title by default;
- normalize only when a profile explicitly declares title-derived matching useful;
- strip volatile suffixes/prefixes through profile logic before HMAC;
- never use title token as sole match evidence.

### Browser URL

- never persist full URL by default;
- preferred safe unit is an origin/site identity when genuinely available and allowed by privacy policy;
- query string, fragment, path, typed form values, and page content are excluded from durable matching metadata unless a future ADR explicitly justifies a narrower exception;
- private browsing blocks capture before fingerprint generation for the draft.

### AutomationId / class / control type

- use normalized typed components;
- known framework-level constant values may be stored directly if clearly non-user-derived;
- otherwise HMAC.

### Accessible name/label

Assume user-sensitive. Prefer not to persist. If a profile requires it, normalize minimally and store only HMAC token.

### Geometry

Exact pixel rectangles are brittle. Store only a coarse geometry bucket when it adds useful disambiguation. Geometry is weak evidence and never sufficient alone.

## 7. ContextFingerprintSet v1

```text
ContextFingerprintSetV1
- FingerprintVersion = 1
- ApplicationId
- WindowClassToken?
- WindowTitleToken?
- BrowserOriginToken?
- ControlAutomationIdToken?
- ControlClassToken?
- ControlRole
- FieldLabelToken?
- GeometryBucket?
- AppSpecificToken1?
- AppSpecificToken2?
```

Optional values are absent rather than represented as hashes of empty strings.

## 8. Matching semantics

RecoveryMatcher reasons over individual evidence components. It must not simply compare one composite fingerprint hash because that makes graceful profile-aware matching impossible.

Positive evidence, missing evidence, and contradictory evidence are distinct.

## 9. Key rotation

MVP does not perform transparent fingerprint-key rotation while recoverable drafts exist. Rotation procedure:

1. stop observation;
2. discard all recoverable records;
3. replace protected fingerprint key;
4. resume.

A future version may introduce dual-key migration through a dedicated ADR.

## 10. Tests

Required tests:

- deterministic token for same key/kind/normalized value;
- different signal namespace => different token;
- different installation key => different token;
- raw title/URL/label never appears in persisted fixture;
- malformed/unavailable key => fail closed;
- profile normalization changes require fingerprint version/profile version changes where needed;
- full URL query/path never enters default persisted fingerprint input.
